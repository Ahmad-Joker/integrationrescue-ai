# Judge Q&A

**Is this real AI or a script?** The live agent is Google Gemini using function calling. It picks every tool call,
hypothesis and repair, and its path differs from run to run. A separate rule-based baseline exists for tests and
comparison. It is always labelled "DETERMINISTIC BASELINE (no LLM)" and is never presented as the AI. Tool execution,
sandboxing and verification are identical in both. Live results are only the ones in `TECHNICAL_EVIDENCE.md`.

**Why is this an agent and not an automation?** An automation runs a fixed playbook for a known failure. Here the
failure is unknown when the ticket arrives. The agent decides what to look at next based on what it found, forms and
refutes hypotheses, decides whether a fix is needed at all (3/3 no-action cases), and recognises when it cannot know
(outage → INDETERMINATE).

**What stops the agent from "fixing" by cheating?** It cannot edit tests, the verifier, or anything outside two
allow-listed paths. The regression test is generated by our code and must fail before the patch. The verifier reads
the database read-only and derives the expected plan from billing. A patch granting Pro to everyone is caught by the
existing suite (tested).

**What happens if the model is down or out of quota?** The incident shows MODEL UNAVAILABLE and ends ESCALATED or
DIAGNOSED, never VERIFIED (tested). Evaluations exclude such runs as infrastructure errors rather than counting them.

**What about prompt injection in tickets?** Ticket, log and API content is data. Tools are typed and phase-gated. This
is tested with a ticket that orders the agent to read `.env` and mark itself verified. Live Gemini handled the
injected-ticket variant 2/2.

**Duplicate charges?** Payments are idempotent. Replay redelivers the stored event and never charges. The verifier
asserts exactly one successful charge and one grant. This is tested with duplicate-delivery and lost-ack faults.

**Did the AI ever do something unsafe?** Yes, and that is why the guardrails are in code. In live run 3 Gemini trusted
a new signing key taken from the incoming event without checking that billing had announced it. The orchestrator now
rejects such keys whatever the model proposes, with a test for a forged key.

**How reliable is it?** Configuration and trust-change repairs: 11/11 after the fix. Code repairs: 0/5 scored. That is
the main technical gap, and we say so. Samples are small and the model is a free-tier lite model.

**Isn't this what Datadog, Sentry or coding agents do?** They diagnose telemetry or fix code. Our narrow claim is
verifying the cross-system business outcome independently of the AI. The comparison with a coding agent is designed
but not yet run, so we make no superiority claim.

**Customers?** None yet. This is a prototype on simulated services with fictional data. Interviews are planned
(`PROBLEM_VALIDATION_PLAN.md`).

**Can I try it?** See `docs/JUDGE_ACCESS.md`: public URL once deployed, or run the container locally.
